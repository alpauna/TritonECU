# Target vehicle: 1999 Ford F-150, 5.4L Triton / 4R70W

Replacing the EEC-V PCM and its integrated transmission control with the
ESP-ECU running on a Waveshare ESP32-P4-WIFI6.

Everything below is either verified against the sources noted or explicitly
flagged as **[CONFIRM ON TRUCK]**. Nothing here should be wired up on the
strength of this document alone — the point of Phase 0 is to check it.

---

## 1. What we are replacing, and what we are not

| Module | Fate |
|---|---|
| PCM (EEC-V) | **Replaced.** Engine + transmission control. |
| Transmission control | **Replaced.** It lives inside the PCM on this truck; there is no separate TCM. |
| GEM (Generic Electronic Module) | **Kept.** C239/C240/C241 — must keep receiving what it expects over SCP. Note the truck may have a Central Timer Module instead; **[CONFIRM]** |
| Instrument cluster (HEC) | **Kept.** Also hosts PATS on this truck. |
| ABS module | **Kept.** |
| PATS transceiver | **Kept, ignored.** C297 — the reader only; the logic is in the cluster |
| Transfer case shift relay module | **Kept.** C221 — self-contained, not an ECU function |
| Inertia fuel shutoff switch | **Kept, in circuit.** C204 — safety device in the fuel pump path |

### PATS is not an obstacle here

The 1999 F-150 uses **PATS Type C**: the anti-theft logic lives in the
instrument cluster, which authorises the *PCM* over SCP. PATS immobilises the
truck by telling the Ford PCM not to fuel.

A replacement ECU never asks. There is nothing to defeat, decrypt, or spoof —
the enable path simply is not in the circuit any more. This is the same thing
every standalone engine management install does. Expect the theft indicator to
behave oddly (it may flash, since the cluster is looking for a PCM that no
longer answers); that is cosmetic. **[CONFIRM ON TRUCK]** whether the cluster
does anything more than blink the lamp.

So: no work needed on the security module, and no need to determine whether its
messages are encrypted.

### The cluster is the integration risk — not the GEM

**Corrected.** Earlier revisions of this document treated the GEM as the main
SCP risk. The factory data-line sheet shows the **SCP bus carries only the PCM
and the instrument cluster**. The GEM sits on **ISO 9141** (circuit 70) along
with the restraints, RAP and 4WABS modules, and shares no bus with the PCM.

So the GEM cannot be starved of SCP messages, because it never received any.
Whatever it needs from the PCM arrives hardwired or not at all — PCM pin 68 is
a discrete *"VSS+ out to cruise"* output, which fits that reading.

The real risk is the **instrument cluster**: it is the only other device on
SCP, it hosts PATS, and it is the likely source of the tach and speedometer
readings. **Capture what the OEM PCM transmits to it before removing it.**
That is Phase 0.

See `1999-Ford-F150-4wd-5.42v/oem-connectors.md`.

## 2. Engine and transmission facts

**5.4L Triton V8 (2V), EEC-V**

| Item | Value | Source |
|---|---|---|
| Cylinders | 8 | — |
| Firing order | 1-3-7-2-6-5-4-8 | Ford modular 2V **[CONFIRM ON TRUCK]** |
| Ignition | **Coil-on-plug, 8 individual coils** (C1011–C1018) | verified from the factory component-location sheet |
| Coil drivers needed | **8**, one per cylinder, individually timed | follows from COP |
| Injection | Sequential, 8 injectors, high-impedance saturated | — |
| CKP | **36-1 variable reluctance** on the crank, 10° resolution | verified |
| CMP | **Variable reluctance**, cam sync | verified |
| Load sensing | **Mass air (MAF)** — decision: keep the OEM MAF | — |
| Engine temperature | **CHT** (cylinder head temp, C179), not ECT | verified |
| Knock sensor | **Present** — C103 | verified from component-location sheet 2 |

**The VR finding matters.** Both crank and cam sensors are variable-reluctance:
they generate a self-powered sine wave whose amplitude scales with speed —
roughly a few hundred millivolts at cranking, tens of volts at high rpm. That
cannot drive a GPIO. It needs a dedicated VR conditioner (adaptive-threshold
zero-crossing detector) ahead of the MCU. The current firmware assumes clean
digital edges on `PIN_CRANK`/`PIN_CAM`; on this truck that assumption is wrong
and is a hardware gap, not a software one.

|---|---|---|
| SSA, SSB | on/off | shift scheduling |
| TCC | PWM | converter lockup |
| EPC | PWM (variable force) | line pressure — governs shift feel |
| TSS | speed input | turbine shaft; added to the 4R70W around 1999 — verified |
| OSS | speed input | output shaft; also the cluster's road-speed source |
| TR sensor | multi-position digital | park/neutral/gear range |

## 4. The binding constraint: this board has 27 GPIOs

The ESP32-P4 die has 55 GPIOs. The Waveshare ESP32-P4-WIFI6 breaks out **27**,
because the rest are committed on-board:

| GPIO | Committed to |
|---|---|
| 9–13 | I2S audio codec + microphone |
| **14–19** | **SDIO link to the ESP32-C6 — this is Wi-Fi/BLE** |
| 35–38 | boot strapping, UART0 to the CH343 |
| 39–45 | SD card on SDMMC slot 0 |
| 53, 54 | speaker amp enable, C6 reset |

Two knock-on effects:

1. **GPIO16–19 are ADC1 channels 0–3.** The Wi-Fi link eats them. Only ADC1
   CH4–7 (GPIO20–23) survive. ADC2 (GPIO49–52) is available and, unlike on the
   ESP32-S3, is genuinely usable — the P4 has no on-die radio to contend for it.
   That is 8 native ADC channels total, at 12 bits, with the P4's mediocre
   linearity.
2. **GPIO24/25 are the USB D-/D+ pair** and should be left alone, leaving **25**
   truly free pins.

### The budget does not close as-is

*(Superseded by [`pin-budget.md`](pin-budget.md), which works this through with
two MAX9926s and the full 4-VR complement.)*

Counting what a sequential 8-cylinder build with full trans control and SCP
needs on real pins:

| Group | Pins |
|---|---|
| CKP, CMP | 2 |
| Coil drivers (coil-on-plug) | 8 |
| Injectors (sequential) | 8 |
| TSS, OSS | 2 |
| SPI (SCK/MOSI/MISO + 2 CS) | 5 |
| AD7606B CONVST, BUSY | 2 |
| I2C | 2 |
| J1850 TX_P, TX_N, RX | 3 |
| TCC, EPC PWM | 2 |
| IAC PWM | 1 |
| Tach, road speed to cluster | 2 |
| **Total** | **37** |

**37 needed against 25 available.** This is the central design problem, and it
is a property of the *carrier board*, not the P4 chip.

### Three ways out

**A — Accept the compromises (fits, barely).**
- Semi-sequential injection: 8 injectors driven as 4 paired banks. Saves 4.
  On a 2V truck engine this costs very little; the OEM is sequential, but
  paired injection is well-proven at this power level.
- Paired ignition: drive the 8 COP coils as 4 companion pairs, wasted-spark
  style. Saves 4. The spare spark lands on an exhaust stroke and is harmless,
  but it throws away COP's real advantage — per-cylinder timing — and doubles
  every coil's duty. A compromise for the bench, not for the truck.
- Drive the cluster over SCP instead of discrete tach/speed wires, if Phase 0
  shows the cluster takes them that way. Saves 2. **[CONFIRM ON TRUCK]**
- Move every static or slow output (relays, MIL, SSA/SSB, EGR, HEGO heaters,
  AD7606B RESET/OS0-2/RANGE) onto the existing MCP23S17 SPI chain — the repo
  already supports this, and it costs no extra pins beyond the one CS.
- Result: ~29 → still over 25 even with every compromise applied. **Option A no
  longer closes the budget.** With COP the Waveshare carrier is out of I/O for a
  full-function build.

**B — Different P4 carrier.** An ESP32-P4-Nano, or a bare ESP32-P4NRW32 on a
custom carrier, breaks out far more GPIO. Given a custom ECU board is being
built anyway for the drivers and protection, this is the cleanest answer: the
Waveshare board's MIPI/audio/camera hardware is dead weight in a truck.

**C — Split engine and transmission across two modules, linked by CAN.**
Two Waveshare P4 boards: one running the engine, one running the 4R70W, talking
over TWAI (the P4 has two controllers). Roughly 25 pins for the engine node and
12 for the transmission node — both fit comfortably, with headroom.

**This is how the truck was already made to work.** The previous MegaSquirt
build on this same vehicle used an **MS3Pro PNP for the engine and a MicroSquirt
for the transmission, linked over CAN** — see
[`1999-Ford-F150-4wd-5.42v/eec-v-pinout.md`](1999-Ford-F150-4wd-5.42v/eec-v-pinout.md),
where the MicroSquirt pin assignments are called out against SS1, SS2, CSS, TCC,
EPC, TFT, TSS, OSS and the four TR inputs, and the closing note specifies the
two units as the ends of the CAN bus.

It is also the natural software split: transmission control is soft real-time
and self-contained, while spark and injection timing are hard real-time. Putting
them on separate cores of separate chips means a busy web request can never
delay a spark event.

**Superseded** — see [`v1-scope.md`](v1-scope.md). Option C existed because the
Waveshare carrier exposes only 25 usable pins. On a raw ESP32-P4 the whole
thing, engine *and* transmission, fits on one board in 37 pins. There is no
second node.

Original recommendation: **C**, revised. It needs no custom silicon carrier, no
compromise on sequential injection or per-cylinder coil-on-plug timing, and it
reproduces an architecture already proven on this exact truck. Two boards cost
less than one custom carrier respin.

B remains the better long-term answer if a custom board is being made anyway —
a bare ESP32-P4NRW32 removes the constraint permanently. But C gets a running
truck sooner using hardware already on the bench.

## 5. Peripherals

### 5.1 Analog front end — AD7606B

The P4's own ADC is not good enough to run an engine on: 12-bit, single-ended,
0–3.3 V, no input protection, and mediocre linearity. Automotive sensor lines
are 0–5 V, sit in a harness full of injector and coil transients, and want to be
sampled simultaneously.

The **AD7606B** answers all of it, and there is already a bench-validated
driver for it in `~/Claude/LxScanner/firmware-teensy`:

- 8 channels, **16-bit, simultaneous sampling** — every sensor captured at the
  same instant, which matters when correlating MAF and TPS against crank angle.
- **True bipolar ±10 V / ±5 V inputs**, so 0–5 V sensors connect directly with
  no scaling op-amps.
- **On-chip input clamps to ±16.5 V** — real protection against a harness fault.
- **True differential inputs**, which the MAF actually requires: it has a
  dedicated signal return (circuit 968) separate from its power ground, so the
  hot-wire supply current's ground drop cancels only if both lines are measured
  against each other. The P4's single-ended ADC cannot use that return at all.
  See `1999-Ford-F150-4wd-5.42v/oem-connectors.md`.
- Hardware oversampling (OS0–2) for free noise reduction on slow channels.
- Single-supply, on-chip reference.

Porting the driver is straightforward: it is plain SPI plus CONVST/BUSY/RESET
GPIO, already proven at 8 MHz SPI_MODE0. The Teensy code streams frames over
USB; here it becomes a sampling task feeding `SensorManager`.

Reuse the existing code as the starting point rather than rewriting it — it has
already been validated against a known ±1.24 V reference on the bench
(2026-08-27/28), including the SPI mode and the reset timing.

### 5.2 VR conditioning for CKP and CMP

Needed, and currently missing. **MAX9926UAEE+** — dual-channel adaptive VR
interface, the part rusEFI uses on their published VR conditioner board with a
full BOM. Details and channel count in
[`1999-Ford-F150-4wd-5.42v/vr-conditioning.md`](1999-Ford-F150-4wd-5.42v/vr-conditioning.md).

OSS is confirmed VR (the MegaSquirt build conditions it with an LM1815). CMP is
unresolved — it may be Hall. TSS turned out not to exist on this transmission.

### 5.3 SCP / J1850 PWM

The '99 F-150 is pre-CAN. Both OBD-II *and* the internal module bus are **SAE
J1850 PWM at 41.6 kbps** on DLC pins 2 and 10 — verified from the factory
schematic: C228 pin 2 = circuit 914 BUS (+), pin 10 = circuit 915 BUS (−). One
transceiver serves both jobs: talking to a scan tool, and keeping the GEM and
cluster fed.

The DLC also carries an **ISO 9141 K-line** on pin 7 (circuit 70). It does not
affect the ECU design, but it means J1850 is not necessarily the whole bus
picture on this truck — see `1999-Ford-F150-4wd-5.42v/oem-connectors.md`.

There is already a designed front end for this in
`~/Claude/LxScanner/docs/j1850_multiprotocol.md`, adapted from the MIT-licensed
OpenJ1850 project and explicitly aimed at a Ford F-150:

- TX: **DRV8837** H-bridge as a differential line driver (TX_P/TX_N driven
  complementary; no single-chip J1850 PWM transceiver exists commercially).
- RX: **TLV7031** comparator across PWM+/PWM−.
- Runs from 5 V; no boost rail needed for PWM (that was only for VPW).
- The reference schematic's own warning is worth repeating: the PWM side is
  experimental and expects per-vehicle tuning. Also, if nothing decodes, try
  swapping DLC pins 2 and 10 — polarity varies by implementation.

**Do not use the MC33390 for this truck.** It is in `~/Documents` and looks like
the obvious answer — a purpose-built J1850 transceiver IC that beats a
repurposed H-bridge. It is the wrong variant: the 33390 is **single-wire VPWM
at 10.4 kbps**, which is the *GM* flavour of J1850. Ford SCP is **two-wire
differential PWM at 41.6 kbps**. The part is useful for GM coverage in the
LxScanner scanner; it cannot talk to this F-150 at all.

### 5.4 Injector and coil drivers

- **Injectors:** high-impedance saturated. Logic-level N-channel MOSFETs with
  clamped avalanche-rated drains, or a purpose-built quad driver.
- **Coils:** the '99 coil packs use external ignition drivers in the PCM.
  Confirm whether these are dumb 2-wire coils needing an IGBT per channel or
  smart coils with logic-level input. **[CONFIRM ON TRUCK]** — this changes the
  driver design completely.

## 6. Plan

### Phase 0 — Listen before touching anything

Wire the J1850 PWM transceiver to the DLC with the OEM PCM still installed and
the truck running. Record the bus. The DLC supplies permanent 12 V on pin 16
and grounds on pins 4/5, so the rig plugs in like a scan tool — no splicing,
completely non-invasive. Deliverable: a catalogue of what the PCM
transmits, at what rate, to the GEM and cluster — RPM, road speed, coolant,
engine-running state, MIL status.

This is the highest-value step and the lowest risk. It validates the
transceiver, answers whether the cluster's tach and speedo are SCP-driven or
hardwired (which decides the pin budget), and produces the message set the
replacement must reproduce. It also does not require the ECU to work at all.

### Phase 1 — Analog front end
Port the AD7606B driver from the Teensy project into `SensorManager`.
Bench-verify against known voltages before anything goes near the truck.

### Phase 2 — Sync
VR conditioners on CKP/CMP. Prove 36-1 decode and cam sync on a signal
generator, then on the engine cranking with fuel and spark disabled.

### Phase 3 — Run the engine
Injector and coil drivers. Fuel and spark on the bench with a scope, then in
the truck.

### Phase 4 — Transmission
4R70W: SSA/SSB, TCC, EPC, TSS/OSS, TR, TFT.

### Phase 5 — Bus integration
Transmit the Phase 0 message set so the GEM and cluster behave, and answer
OBD-II mode 01/03 requests for a scan tool.
